# フィードバックに基づく改善提案

**日付**: 2025-11-08
**目的**: レビューで提示された改善要望を整理し、実装計画を策定する

## フィードバック概要

「行政事業レビューのサンキー図、ビジュアライゼーションとして面白い。あと数歩デザイン面やデータをブラッシュアップしたら広く公開できそう」という評価をいただきました。

## 改善提案の分類と優先度

### Phase 1: データ品質とソート機能（即座に実装可能）

#### 1.1 2014-2015年度データの除外 ✅ **優先度: 高**
- **現状**: 2014-2024年の全年度データを表示
- **課題**: 2014, 2015年度はデータ品質が低い
- **対応**:
  - 対象年度を2016-2024に変更
  - トップページの年度選択から2014, 2015を非表示
  - 前処理スクリプトは2014, 2015も処理（将来的な参照用）
- **実装箇所**:
  - `types/rs-system.ts`: `AVAILABLE_YEARS`の定義変更
  - `app/page.tsx`: 年度選択UIから除外
  - `scripts/preprocess-data.ts`: コメント追加（データは生成するが非推奨と明記）

#### 1.2 支出順にソート ✅ **優先度: 高**
- **現状**: サンキー図の府省庁ノードは金額降順でソート済み（[preprocess-data.ts:196-197](../scripts/preprocess-data.ts#L196-L197)）
- **課題**: より視覚的にわかりやすくするための調整が必要か確認
- **対応**:
  - 現在の実装を確認し、必要に応じてソート順を調整
  - 支出先レベルでもソートを適用

### Phase 2: サンキー図の多階層化（設計＋実装が必要）

#### 2.1 3-4カラムのサンキー図 🔶 **優先度: 高**
- **現状**: 2カラム（年度予算合計 → 府省庁）
- **提案**: 多階層化でより詳細な資金の流れを可視化
  - **レベル1**: 年度予算合計
  - **レベル2**: 府省庁
  - **レベル3**: 事業（Top10 + その他）
  - **レベル4**: 支出先（Top10-20 + その他）

**実装方針**:
```typescript
// 階層別のビュー定義
type ViewLevel = 'ministry' | 'project' | 'expenditure';

interface SankeyViewConfig {
  level: ViewLevel;
  columnCount: number; // 2, 3, or 4
  maxNodesPerColumn?: number; // Top N + その他
}
```

**データ構造**:
- 既存の`ministry-projects.json`（府省庁→事業Top10）を活用
- 既存の`project-expenditures.json`（事業→支出先Top20）を活用
- サンキー図生成ロジックを階層対応に拡張

**UI設計**:
- ビューレベル切り替えボタン（省庁レベル/事業レベル/支出先レベル）
- URLパラメータで状態管理: `?level=project&ministry=財務省`

#### 2.2 「その他」の展開機能 🔶 **優先度: 中**
- **現状**: 「その他」はクリックしても展開されない
- **提案**: 「その他」をクリックすると、残りの項目を表示
- **実装方針**:
  - モーダルまたはサイドパネルで「その他」の内訳を表示
  - ページネーション付きリスト形式
  - オプション: 「その他」を展開してTop20, Top30...と動的に拡張

### Phase 3: 事業詳細情報の充実（中期実装）

#### 3.1 事業詳細へのリンク ✅ **優先度: 高**
- **現状**: 事業レポート機能は実装済み（`/reports`）
- **課題**: サンキー図から事業詳細へのナビゲーションが不明瞭
- **対応**:
  - 事業ノードクリック時に事業詳細ページ（`/reports/[projectKey]`）へ遷移
  - 既存実装: [SankeyChart.tsx:184-186](../client/components/SankeyChart.tsx#L184-L186) で実装済み
  - 改善点: より明示的なUI（ツールチップに「クリックで詳細を表示」と追記）

#### 3.2 RSシステムへの外部リンク 🔶 **優先度: 中**
- **現状**: 事業詳細ページには外部リンクなし
- **提案**: 元のRSシステムへのリンクを追加
- **実装方針**:
  - 事業詳細ページに「行政事業レビューシートを見る」ボタン追加
  - リンク形式: `https://www.gyoukaku.go.jp/review/...` （URLパターン要調査）
  - 必要データ: 予算事業ID、府省庁コード、年度

### Phase 4: 企業・自治体レベルの集約（長期実装）

#### 4.1 支出先（企業・自治体）でのアグリゲーション 🔷 **優先度: 中**
- **現状**: 支出先は事業ごとに個別表示
- **提案**: 支出先名でグルーピングし、「どの企業にどの省庁からいくら流れたか」を可視化
- **実装方針**:
  - 新しいビュー: 「支出先起点ビュー」を追加
  - データ構造: 支出先 → 事業 → 府省庁の逆引きインデックス
  - 前処理スクリプトで`expenditure-index.json`を生成
  - URLパターン: `/expenditures/[expenditureName]`

**データ構造例**:
```typescript
interface ExpenditureAggregation {
  expenditureName: string;
  totalAmount: number;
  projects: Array<{
    projectName: string;
    ministry: string;
    amount: number;
    years: Year[];
  }>;
}
```

#### 4.2 企業から先のトレース（基金など） 🔷 **優先度: 低**
- **現状**: 5-1（支出先情報）までしか追跡できない
- **提案**: 基金や特別会計の先まで追跡
- **課題**:
  - 現在のCSVデータには基金の再配分先データが含まれていない
  - 別データソースの統合が必要
- **実装方針**:
  - まずは5-2（支出ブロックのつながり, 2024年のみ）を活用
  - 将来的に外部データ（基金の再配分情報）を統合

#### 4.3 自治体データとの紐づけ（長期・コミュニティ機能） 🔷 **優先度: 低**
- **提案**: Wikipedia的な仕組みで、ユーザーが自治体データを登録
- **実装方針**:
  - フェーズ1: 静的データとして自治体情報をマニュアル追加
  - フェーズ2: ユーザー投稿機能（要認証、モデレーション）
  - フェーズ3: AI妥当性評価機能
- **技術要件**:
  - データベース（Prisma + PostgreSQL/Supabase）
  - ユーザー認証（NextAuth.js）
  - モデレーション機能
  - AIレビュー機能（LLM API連携）

### Phase 5: 多階層ビューの実装（長期実装）

#### 5.1 レベル別ビューの実装 🔶 **優先度: 高**
1. **省庁レベルのビュー** （現在実装済み）
   - 年度予算 → 府省庁

2. **事業レベルのビュー** （データは準備済み、UI実装が必要）
   - 年度予算 → 府省庁 → 事業（Top10 + その他）
   - データソース: `ministry-projects.json`

3. **支出先レベルのビュー** （データは準備済み、UI実装が必要）
   - 年度予算 → 府省庁 → 事業 → 支出先（Top20 + その他）
   - データソース: `project-expenditures.json`

**実装順序**:
1. ビュー切り替えUI実装（タブまたはセレクター）
2. 3カラムサンキー図の実装（府省庁→事業）
3. 4カラムサンキー図の実装（府省庁→事業→支出先）
4. 各ノードのクリックインタラクション改善

### Phase 6: 収入サイドの可視化（長期・データ調達が必要）

#### 6.1 税収・租税特別措置の可視化 🔷 **優先度: 中**
- **提案**: 「我々の税金はどこから来てどこへ行くのか」の完全な流れ
- **必要データ**:
  - 一般会計・特別会計の収入データ
  - 租税特別措置法の減税情報（財務省に問い合わせ中）
- **実装方針**:
  - 左端に収入源を追加（所得税、法人税、消費税など）
  - 5カラム以上のサンキー図: 収入 → 年度予算 → 府省庁 → 事業 → 支出先

## 技術的考慮事項

### パフォーマンス
- 3-4カラムサンキー図はノード数が増えるため、レンダリング最適化が必要
- 大規模データの場合は仮想化（react-window等）を検討
- 「その他」展開時のデータフェッチ戦略（事前読み込み vs オンデマンド）

### データサイズ
- 現在: 年度別JSONは約11KB（2カラム）
- 3カラム: 推定30-50KB（事業Top10含む）
- 4カラム: 推定100-200KB（支出先Top20含む）
- 必要に応じて圧縮（gzip）やコード分割を検討

### ユーザビリティ
- モバイル対応: 3-4カラムは横スクロール必須
- ズーム・パン機能の追加を検討
- レベル切り替え時のアニメーション
